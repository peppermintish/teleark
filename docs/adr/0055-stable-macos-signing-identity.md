# ADR 0055: Stable self-signed macOS release identity

Status: accepted, 2026-09-22

Self-signed code signing establishes continuity between TeleArk releases for macOS Keychain access. A new identity every build, ad-hoc signing, or unsigned code cannot provide that continuity. We generate one RSA-3072 identity, commit only its public certificate, and retain the private key outside the checkout and in the repository Actions secret store.

App and standalone executable use `app.teleark.desktop` and a designated requirement pinned to that certificate. Packaging fails closed when the identity is missing or mismatched. Each signing run attempts to import the PKCS#12 identity into a disposable private Keychain, verifies the pinned public fingerprint among all certificate/private-key identities before applying the restricted partition list, temporarily adds that Keychain to the user search list, verifies both outputs, restores the prior search list, and removes the temporary keychain and key files. If PKCS#12 import is rejected, the script extracts typed PEM files and imports the pair through `certtool`. The identity lookup must not use the valid-only filter: system certificate trust is independent of this pinned self-signed identity. Successful signing and signature verification remain required. No blanket Keychain ACL or system-root trust change is used. Installer payload verification handles the distinct standalone and bundle signatures.

The 2026-09-23 import correction supersedes the fallback's separate `security import` calls for the PEM certificate and key. On the hosted macOS 15 runner those calls produced a matching identity listing, but `codesign` could not use it. Importing the pair together with Apple's `certtool` still failed to sign in a hosted package preview. A subsequent hosted probe established that `codesign --keychain` alone did not make the private key discoverable: signing by hash and by name failed while the temporary Keychain was absent from the user search list, then signing by hash with the same explicit Keychain succeeded after adding it. The signer therefore registers that Keychain only for the signing interval and restores the original list on exit. The persistent certificate and designated requirement remain unchanged.

This reduces repeated prompts for items created by the same signed identity. It cannot grant access to another identity’s items, unlock a user’s Keychain, or provide Apple notarization/Gatekeeper trust. Runtime uses noninteractive access and actionable failure instead. Existing recovery material is retained on failure. Certificate rotation must include continuity/recovery planning and cannot silently replace the pinned identity.

Evidence: native synthetic signing test signs two resource versions with the same designated requirement, verifies standalone code equivalence and rejects modified resources. The [macOS 15 diagnostic run](https://github.com/wood-made/teleark/actions/runs/35818686587) isolated the search-list requirement, and the [hosted synthetic regression](https://github.com/wood-made/teleark/actions/runs/35819065340) passed with the corrected signer. Full release workflow verifies both universal slices and installer upgrades.

Primary references: [Apple code signature guide](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html), [TN2206 OpenSSL identity import](https://developer.apple.com/library/archive/technotes/tn2206/), and [TN3127 requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).
