# ADR 0004: Use Framed AES-256-GCM Envelope Encryption

- Status: Accepted (algorithm); exact v1 bytes remain provisional
- Date: 2026-08-24

The historical provisional/review prerequisite below is superseded by [ADR 0017](0017-versioned-automatic-migrations.md). The cryptographic design remains in effect.

## Context

TeleArk needs client-side confidentiality and integrity for files much larger than memory. Password change should not re-encrypt stored content, recovery must not depend solely on an OS credential store, and corruption/reorder/truncation must fail safely. A monolithic AEAD operation over a roughly 1900 MiB application part would require unacceptable memory and resume behavior. AES-GCM nonce reuse is catastrophic.

## Decision

Use maintained implementations of AES-256-GCM over bounded crypto frames, with BLAKE3 whole/part hashes and Argon2id password derivation. Use envelope encryption: password/recovery KEKs unwrap a random Vault Master Key, which unwraps a fresh random File Key per package. Derive a domain-separated content key for each fresh random part-instance identity and construct a versioned 96-bit nonce from part/frame indices. Restarted source encoding uses a new part-instance key; it never risks encrypting changed plaintext under an old key/nonce pair.

Do not implement AES/GHASH/GCM/Argon2/RNG primitives. Stream frames and authenticate package/part/frame/layout data as AAD. Exact headers, KDF domains, limits, and key-wrap behavior are specified provisionally in `CRYPTO_FORMAT.md` and cannot be called stable until review, vectors, tamper tests, and fuzzing pass.

## Consequences

- Memory remains bounded to a small number of frame buffers.
- Every frame can authenticate independently while manifest/layout checks detect omission, reorder, and truncation.
- Password rotation can rewrap the master key rather than all file content.
- Nonce/key identity invariants become persistent-format contracts requiring centralized constants and extensive tests.
- AES acceleration may improve throughput on supported crate/target/CPU combinations, but cannot be promised universally.
- Loss of all valid unlock/recovery material makes ciphertext unrecoverable by design.
- A future algorithm change requires explicit suite/version support rather than silently changing v1.
