# ADR 0025: Fixed storage channel, file-local damage and retained key epochs

Status: Accepted. The lock-triggered cancellation portion is superseded by [ADR 0026](0026-session-unlock-and-task-key-leases.md). Supersedes ADR 0015's requirement that intact management markers authorize use of an already bound channel, and ADR 0008's single-local-key-record restriction. Manifest authentication and the remote privacy/ownership checks remain mandatory.

## Decision

An account keeps one positive Telegram channel ID. The `storage-channel.v2.account.<account>` setting has the exact JSON object `{"version":2,"channel_id":<positive integer>}`. Readers automatically promote a valid v1 decimal binding after successful remote validation; they retain the old value. A different channel cannot replace an existing binding. A title is never evidence for adopting a channel. A missing bound channel remains unavailable; it never triggers creation of a replacement.

Local binding selects the peer; it does not authorize network mutations. Fresh account, creator, private broadcast, sole-member/admin, bot, discussion and TTL checks are performed by Telegram. Missing, invalid or unpinned identity management records are repairable metadata damage and do not make independently authenticated file content unusable. Unsafe configuration, lost access and newer identity formats block affected operations. Repair requires an explicit UI confirmation, operates on the original channel and preserves file messages, membership, privacy and user-selected titles. It finds or sends an identity record, pins it, restores the description pointer and reads back the result. A persisted nonzero SendMessage random ID is reused across interrupted attempts; pin/about RPCs are idempotent. Discovery is bounded. Cross-device simultaneous initial creation still has no Telegram atomic uniqueness primitive.

Mute/archive is a separate, explicit one-shot operation for this peer only. It reads back the folder and mute state before completion; no loop restores the user's later preferences. It does not modify global archive preferences. RPCs follow the public [Telegram notification API](https://core.telegram.org/method/account.updateNotifySettings) and peer-folder API, using the license-compatible public grammers types.

## File health

The local inventory retains authenticated **encrypted** manifest envelopes and opaque account/channel/message/key identities. It stores no decrypted manifest names, file keys or master keys. Upload completion persists the already re-read envelope before reporting success. Remote deletion or corruption never replaces the preserved envelope. Existing files predating this inventory are enrolled as they are successfully authenticated; data deleted before enrollment cannot be reconstructed by this feature.

File health distinguishes unchecked, message presence confirmed/indexed, missing parts, missing remote manifest, missing key and invalid/unsupported manifest. Presence is not a claim of end-to-end content authentication; restoration still authenticates all ciphertext. Missing parts affect only their file. Explicit checks read history in pages of 100 and probe at most 100 message IDs per request; they then keyset-page the retained inventory to include deleted manifests. Successfully completed observations persist. Cancellation/network failure does not classify an unexamined object as missing. Each full run has an opaque token so the retained-inventory pass skips records already handled in that run.

A retained, independently cancellable health owner keeps long checks off the UI, Vault command owner and Telegram reactors. Only one full check per Vault instance may run. The key snapshot is at most the active key and one historical key; An explicit cancellation releases it after the current cancellable request returns; session lock preserves the admitted check under ADR 0026. UI projections retain at most 1,000 files / 16 MiB and disclose the display limit; the explicit history check continues beyond it without accumulating all results. Stored ciphertext is paged one envelope at a time (maximum 16 MiB per record). Routine navigation uses revisioned manifest caching and durable update evidence, not a full remote history scan.

## Keys and migration

SQLite schema 15 adds the retained key-epoch table, encrypted inventory and message-presence observations. It automatically copies the previous singleton wrappers into the epoch table inside the existing transactional migration machinery. Skipped upgrades apply in order. Failure leaves the old version and records usable; newer databases are rejected intact. No manifest, wrapped-key or recovery-bundle bytes change meaning: manifest v1, current password/recovery wrappers and recovery bundle v1 remain readable/writable.

A key epoch is the manifest's existing 16-byte `vault_id`, not its password/recovery wrap generation. Password and recovery rotations keep the epoch; explicitly starting over generates a new epoch and master key. One transaction preserves the old wrappers, inserts the new wrappers and changes the active singleton. UI confirmation states that lost original unlock material makes old data unreadable, requests the new password twice and presents the new recovery bundle for export. Crypto/persistence phases precede expensive work; cancellation is checked before committing. Remote ciphertext remains untouched.

An old recovery bundle can unlock one retained historical epoch without changing the active upload key. A bounded unauthenticated header hint selects a candidate key; the complete manifest must then authenticate before any metadata/locator is used. A matching ID with a wrong key still fails authentication. If the historical bundle was superseded by a locally retained recovery rotation, the exact retained wrapper is required, preserving existing revocation semantics. Losing every unlock path remains unrecoverable; this operation only restores the ability to upload new files in the same channel.

## Evidence

Deterministic tests cover fixed binding selection, metadata health policy, repair-token restart reuse, bounded terminal timelines, skipped migration chains and rollback, atomic epoch switching, recovery of retained old keys, authenticated key routing, file-local deletions, batch limits, persisted partial checks, cancellation and a blocked independent health owner. UI qualification uses synthetic data and separate 900×600 and actual fullscreen sessions in all three locales and both themes. Credentialed Telegram mutation scenarios remain a separate integration qualification; unit tests are not evidence of a live server repair.
