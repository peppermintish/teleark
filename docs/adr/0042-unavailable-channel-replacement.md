# ADR 0042: Recover automatic storage after a bound channel becomes unavailable

Status: Accepted. Supersedes ADR 0025's prohibition on replacing an unavailable bound channel; its restrictions on healthy, unsafe and owner-lost channels remain in force.

## Decision

The account-scoped `storage-channel.v2.account.<account>` record remains a positive ID with the same exact JSON shape and reader. Its former ID is replaced only after a complete bounded Telegram dialog snapshot cannot find it, or a present bound peer is positively classified as unavailable (`channelForbidden`, `left`, or a channel-unavailable RPC). No title or local cache identifies a replacement. A present channel with missing creator rights, unsafe privacy, damaged management information or an unsupported newer identity continues to block or permit only its already-defined operations; none silently triggers replacement. An incomplete/truncated roster, uncertain RPC result, candidate conflict or uncertain creation does not release the binding.

After the unavailable result, Runtime performs a fresh complete discovery without a preferred ID. Exactly one remotely verified managed candidate is adopted; when none exists, the existing ambiguity-guarded Telegram creation and readback path creates one. More than one candidate blocks setup. Only after remote verification does Storage atomically compare the saved old account ID and write the new v2 setting; a racing replacement fails without overwriting the winner. A failed remote operation or failed local write preserves the old binding for a restartable retry. No setting is cleared in advance, no old records/keys are rewritten, and existing file/transfer identities retain their old channel scope. The new channel is for new writes, not a recovery of remote objects removed with the old channel. Local copies and authenticated historical metadata remain untouched.

The setup owner emits a bounded phase timeline for binding lookup, complete dialog read, owner/privacy check, replacement discovery, creation/branding, saving and terminal outcome. The UI keeps loading/error feedback visible, exposes phase duration and last activity, and explains the replacement and remote-data loss in the synchronized catalogs. This does not imply Telegram proves that a forbidden peer was deleted: the official `channelForbidden` constructor also covers other access failures. No periodic network reconciliation, application schema migration, encrypted format change or automatic remote deletion is introduced.

## Evidence and limits

Deterministic tests cover unavailable versus owner-lost classification, replacement rediscovery decisions, binding compare-and-swap/account isolation/reopen and bounded terminal timeline. Existing creation/readback/ambiguity tests remain. Synthetic UI review covers English compact and actual native full-screen. Credentialed deletion and recreation on a real Telegram account are not implied by fake-peer tests and require an explicit live qualification. Telegram's [channelForbidden](https://core.telegram.org/constructor/channelForbidden) and [getFullChannel errors](https://core.telegram.org/method/channels.getFullChannel) define the adapter cases; no license-incompatible implementation was inspected.
